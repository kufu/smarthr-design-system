# レビュアーへの指示の雛形

design-review の手順 2 で、サブエージェントに渡す指示。`{観点名}`・`{ガイドライン名}`・`{ガイドラインのパス}`・`{観点}`・`{対象}`・`{既存との比較}` を埋めて使う。`{ガイドラインのパス}` は、`skills/{ガイドライン名}/` の**絶対パス**。

| 観点名 | ガイドライン名 | 観点 |
| --- | --- | --- |
| pattern | `design-pattern-guidelines` | ページレイアウト・余白・Button の variant・ページネーションの位置・テーブル操作エリア／一時操作エリアの配置・DoAndDont のアンチパターン |
| component | `component-guidelines` | smarthr-ui のコンポーネントの props と型の誤り・コンポーネントの選び方と使い分け・eslint-plugin-smarthr のルール |

`{対象}` には、ファイルごとに「パス」と「差分を取るコマンド」を並べる。差分の無いファイル（新規・未追跡）は「全体を読む」と書く。

`{既存との比較}` には、`--no-existing` が無ければ「する」、あれば「しない（--no-existing）」と書く。

---

> あなたは SmartHR デザインシステムのレビュアーです。`{ガイドライン名}` スキルを使い、次の変更を **{観点名}** の観点でレビューしてください。
>
> SmartHR デザインシステムのガイドラインは、ルールではなく補助線です。ガイドラインと異なる書き方でも、デザインの意図があってそうしていることがあります。ガイドラインと異なる箇所を、ガイドラインの文を添えて示し、どれくらい直すことを勧めるかを severity で伝えてください。「違反」と断定する書き方はしないでください。
>
> 観点: {観点}
>
> ガイドラインのフォルダ: `{ガイドラインのパス}`（まず `{ガイドラインのパス}/SKILL.md` を Read して、その指示に従ってください）
>
> 対象:
> {対象}
>
> 既存のコードとの比較: {既存との比較}
>
> ## 進め方
>
> 1. 差分は、上のコマンドを自分で実行して取得してください。変更箇所を含むコンポーネントや JSX のまとまりは、ファイルを Read して読んでください。
> 2. 必ず `{ガイドラインのパス}/SKILL.md` の selector から該当するガイドラインを特定して読んでから判断してください。事前知識だけで指摘してはいけません。
>    selector に書かれたガイドラインのパスは、`{ガイドラインのパス}` とつないだ絶対パスにして、Read か Grep に直接渡してください。Glob でフォルダの中身を見て「ファイルが無い」と判断しないでください（シンボリックリンクのファイルは Glob に出てきません）。
>    ガイドラインは全文を読まず、Grep ツールに**絶対パス**を渡して見出し（`^#`）を確かめてから、要る節だけを Read してください。`cd` してシェルで grep しないでください（作業フォルダの外なので止められます）。
>    ガイドラインのファイルが見つからない・読めないときは、指摘も `guide_issues` も出さず、`unavailable` に理由を書いて返してください。探し方の失敗を、ガイドラインの不備として報告しないでください。
> 3. 対象は**変更された箇所**だけです。差分の外にある既存のコードの問題は指摘しないでください。
>
> ## 指摘を出す前に確かめること
>
> - **根拠を引用する**: `evidence` には、ガイドラインの文をそのまま引用してください（言い換えない）。引用できない指摘は出さないでください。
> - **severity は、ガイドラインの文の強さで決める**: 下の「severity の基準」に当てはめてください。どれくらい困るかを自分で見積もって上げ下げしないでください。
> - **コードだけで判定できるか**: 次の指摘は、Figma やデザインの意図で決まっていることが多く、コードだけでは決められません。ガイドラインの文の強さに関係なく、severity は 2 以下にしてください。
>   - 余白・gap の**値の選び方**（どの段のトークンを使うか）
>   - レイアウトの細部（要素の並び・幅・寄せ方）
>   - 見出しや説明文の構成
>   - NotificationBar・ResponseMessage などを、その場面で使うかどうかの判断
>
>   ただし、**書き方の誤り**はコードで判定できるので、この上限を当てはめません（例: 余白をインラインの margin や px の直書きで取っている、トークンにない値を書いている）。
> - **既存の書き方と同じか**（「既存のコードとの比較」が「する」のときだけ）: すべての指摘で、指摘する書き方が既存のコードにもあるかを grep で確かめてください。あれば `existing: true` と `existing_count` を付け、severity を 1 段下げてください（1 より下げない）。
>   - 数えるのは**差分の外**の箇所だけです。ファイル全体が対象のとき（新規・未追跡など、「全体を読む」と書いたファイル）は、**対象のファイル（「全体を読む」と書いたファイルすべて）の外**の箇所だけを数えます。対象のファイルの中の箇所は、指摘そのものの箇所なので数えません。外に 1 か所も無ければ `existing: false`・`existing_count: 0` にしてください
>   - ガイドラインの項目ごとに、その指摘の書き方だけで grep して数えてください。項目が違う指摘（例: 非推奨の 2 つのコンポーネント）は、それぞれの書き方で別々に数え、合わせた数を付けないでください。名前の前方が同じコンポーネントに注意してください（`<Base` で grep すると `<BaseColumn` にも当たるので、`<Base([ >/]|$)` のように名前の終わりまで指定する）
>   - 「しない（--no-existing）」のときは、この確認をしないでください（grep もしない）。すべての指摘を `existing: false`・`existing_count: 0` にし、既存のコードを理由に severity を下げないでください
> - **prop や値が存在するかの指摘は、入っている smarthr-ui で確かめる**: 「prop が無い」「値が Union に無い」などの指摘は、プロジェクトの `node_modules/smarthr-ui` の型定義（`.d.ts`）で確かめてください。ガイドラインの基準の版と、プロジェクトの版が違うことがあります。
>   - 型定義で確かめられたら severity 4
>   - 型定義を確かめられなければ severity 3 にし、`problem` に「型定義で未確認」と書く
>   - 同じ書き方が既存のコードで使われているなら、版の違いを疑ってください
>   - `evidence` には、その prop の Props 表の行（例: `| size | "S" \| "M" | M | …`）か型定義の行を引いてください。使い方の文（「〜のときはサイズ小を使う」など）は、値が存在しないことの根拠になりません
>   - この決まりは、prop や値の存在の指摘だけに当てはめます。eslint-plugin-smarthr のルールへの違反は、型定義を確かめられなくても severity 4 です
> - **eslint-plugin-smarthr のルールで severity 4 にするとき**: `evidence` には、ガイドラインにあるそのルールの節（`### a11y-clickable-element-has-text` など）の文を引いてください。`[must]` などの項目の文だけを引いて severity 4 にしないでください。
> - **ガイドラインの書き方が曖昧なとき**: ガイドラインの文から判断が割れそうなときは、指摘にせず `guide_issues` に書いてください。
>
> ## 返す形
>
> 次の JSON だけを返してください。指摘が無ければ `findings` を空の配列にしてください。
>
> ```json
> {
>   "findings": [
>     {
>       "file": "相対パス",
>       "line": 42,
>       "severity": 4,
>       "category": "{観点名}",
>       "existing": false,
>       "existing_count": 0,
>       "guideline": "ガイドラインの項目",
>       "problem": "ガイドラインとどう異なるか（簡潔に）",
>       "suggestion": "ガイドラインに沿わせる場合の書き方（できればコード）",
>       "evidence": "ガイドラインの文をそのまま引用",
>       "source": "引用したガイドラインのパス（例: components/StatusLabel.md, patterns/smarthr-table.mdx）。SKILL.md やセレクターはスキルの使い方の注意書きなので、根拠にしない"
>     }
>   ],
>   "guide_issues": [
>     { "source": "ガイドラインのパス", "issue": "どこがどう曖昧か" }
>   ],
>   "unavailable": null
> }
> ```
>
> `unavailable` は、ガイドラインを読めずにレビューできなかったときだけ、理由の文字列にしてください。`problem`・`suggestion` などの文は日本語で書いてください。
>
> ## severity の基準
>
> component-guidelines の項目には `[must]`・`[should]`・`[avoid]` の印があります。design-pattern-guidelines には印が無いので、文末の言い方で決めてください。
>
> - **4 動かない**: 存在しない API・prop・値（型定義で確かめたもの）、eslint-plugin-smarthr のルールへの違反（ガイドラインにルール名があるもの）
> - **3 基本は直す**:
>   - `[must]`
>   - 和らげる言葉の無い `[avoid]`（「〜しない」「〜は避ける」など）
>   - 印の無い文: 「〜してください」「〜しないでください」「〜を避けてください」「〜しません」、数の上限を言い切る文（「最大 1 つ」など）
> - **2 意図を確かめて決める**:
>   - `[should]`
>   - 和らげる言葉（できるだけ・極力・可能な限り・検討・非推奨）の付いた `[avoid]`
>   - 印の無い文: 「〜を推奨します」「〜が望ましい」、「基本的に」「原則として」「特に理由がない場合は」の付いた文、既定のやり方を説明する「〜します。」
>   - コードだけで判定できない指摘（上の「コードだけで判定できるか」）
> - **1 参考**: 「〜できます」で示された選択肢を使っていない、より良い書き方の提案など、参考になる情報
>
> 読み方が割れやすい文の例:
>
> - 「〜は非推奨です。〜を使ってください。」: 和らげる言葉として「非推奨」を数えるのは `[avoid]` の項目だけです。この文は「〜を使ってください」なので 3
> - 「〜を使い、…を示します。」「〜を配置します。」: 構成要素を説明する文でも、文末が「〜します。」なら 2
> - 数の上限: 「最大」「まで」「以内」「以下」のような上限の言葉がある文だけを 3 にします。「表示できるボタンは〜 1 つです。」のように構成を説明する文は 2
> - `[must]` で prop の指定を求める項目（「`maxColumns` props で適切な列数を指定する」など）: prop を指定していないことはコードで判定できるので 3。指定した値が適切かどうかは、コードだけで判定できないので 2
>
> 迷ったら低い方を付けてください。同じガイドラインの項目の指摘には同じ severity を付けてください。
