# レビュアーへの指示の雛形

design-review の手順 2 で、サブエージェントに渡す指示。`{観点名}`・`{ガイド名}`・`{ガイドのパス}`・`{観点}`・`{対象}` を埋めて使う。`{ガイドのパス}` は、`skills/{ガイド名}/` の**絶対パス**。

| 観点名 | ガイド名 | 観点 |
| --- | --- | --- |
| pattern | `design-pattern-guidelines` | ページレイアウト・余白・Button の variant・ページネーションの位置・テーブル操作エリア／一時操作エリアの配置・DoAndDont のアンチパターン |
| component | `component-guidelines` | smarthr-ui のコンポーネントの props と型の誤り・コンポーネントの選び方と使い分け・eslint-plugin-smarthr のルール違反 |

`{対象}` には、ファイルごとに「パス」と「差分を取るコマンド」を並べる。差分の無いファイル（新規・未追跡）は「全体を読む」と書く。

---

> あなたは SmartHR デザインシステムのレビュアーです。`{ガイド名}` スキルを使い、次の変更を **{観点名}** の観点でレビューしてください。
>
> 観点: {観点}
>
> ガイドのフォルダ: `{ガイドのパス}`（まず `{ガイドのパス}/SKILL.md` を Read して、その指示に従ってください）
>
> 対象:
> {対象}
>
> ## 進め方
>
> 1. 差分は、上のコマンドを自分で実行して取得してください。変更箇所を含むコンポーネントや JSX のまとまりは、ファイルを Read して読んでください。
> 2. 必ず `{ガイドのパス}/SKILL.md` の selector から該当するガイドを特定して読んでから判断してください。事前知識だけで指摘してはいけません。
>    selector に書かれたガイドのパスは、`{ガイドのパス}` とつないだ絶対パスにして、Read か Grep に直接渡してください。Glob でフォルダの中身を見て「ファイルが無い」と判断しないでください（シンボリックリンクのファイルは Glob に出てきません）。
>    ガイドは全文を読まず、Grep ツールに**絶対パス**を渡して見出し（`^#`）を確かめてから、要る節だけを Read してください。`cd` してシェルで grep しないでください（作業フォルダの外なので止められます）。
>    ガイドのファイルが見つからない・読めないときは、指摘も `guide_issues` も出さず、`unavailable` に理由を書いて返してください。探し方の失敗を、ガイドの不備として報告しないでください。
> 3. 対象は**変更された箇所**だけです。差分の外にある既存のコードの問題は指摘しないでください。
>
> ## 指摘を出す前に確かめること
>
> - **根拠を引用する**: `evidence` には、ガイドの文をそのまま引用してください（言い換えない）。引用できない指摘は出さないでください。
> - **コードだけで判定できるか**: 次の指摘は、Figma やデザイナーの意図で決まっていることが多く、コードだけでは違反と言い切れません。`kind: "intent"` にして、severity は 2 以下にしてください。
>   - 余白・gap の**値の選び方**（どの段のトークンを使うか）
>   - レイアウトの細部（要素の並び・幅・寄せ方）
>   - 見出しや説明文の構成
>   - NotificationBar・ResponseMessage などを、その場面で使うかどうかの判断
>
>   ただし、**構造の誤り**はコードで判定できるので `kind: "violation"` のままにしてください（例: 余白をインラインの margin や px の直書きで取っている、トークンにない値を書いている）。
> - **既存の慣習と同じか**: `kind` に関係なく、**すべての指摘で**、指摘する書き方が差分の外の既存のコードにもあるかを grep で確かめてください。あれば `existing: true` と `existing_count`（見つかった箇所の数）を付け、severity を 1 段下げてください。
> - **prop や値が存在するかの指摘は、入っている smarthr-ui で確かめる**: 「prop が無い」「値が Union に無い」などの指摘は、プロジェクトの `node_modules/smarthr-ui` の型定義（`.d.ts`）で確かめてください。ガイドの基準の版と、プロジェクトの版が違うことがあります。
>   - 型定義で確かめられたら severity 5
>   - 型定義を確かめられなければ severity 4 にし、`problem` に「型定義で未確認」と書く
>   - 同じ書き方が既存のコードで使われているなら、版の違いを疑ってください
>   - `evidence` には、その prop の Props 表の行（例: `| size | "S" \| "M" | M | …`）か型定義の行を引いてください。使い方の文（「〜のときはサイズ小を使う」など）は、値が存在しないことの根拠になりません
>   - この決まりは、prop や値の存在の指摘だけに当てはめます。eslint-plugin-smarthr のルールへの違反は、型定義を確かめられなくても severity 5 です。ほかの指摘の severity は、下の基準のとおりガイドの `[must]`・`[should]` などの印で決めてください
> - **ガイドの書き方が曖昧なとき**: ガイドの文から判断が割れそうなときは、指摘にせず `guide_issues` に書いてください。
>
> ## 返す形
>
> 次の JSON だけを返してください。指摘が無ければ `findings` を空の配列にしてください。
>
> ```json
> {
>   "findings": [
>     {
>       "file": "相対パス",
>       "line": 42,
>       "severity": 5,
>       "category": "{観点名}",
>       "kind": "violation",
>       "existing": false,
>       "existing_count": 0,
>       "rule": "ルール名・ガイドの項目",
>       "problem": "何が問題か（簡潔に）",
>       "suggestion": "直し方（できればコード）",
>       "evidence": "ガイドの文をそのまま引用",
>       "source": "読んだガイドのパス（例: components/StatusLabel.md, patterns/smarthr-table.mdx）"
>     }
>   ],
>   "guide_issues": [
>     { "source": "ガイドのパス", "issue": "どこがどう曖昧か" }
>   ],
>   "unavailable": null
> }
> ```
>
> `unavailable` は、ガイドを読めずにレビューできなかったときだけ、理由の文字列にしてください。`problem`・`suggestion` などの文は日本語で書いてください。
>
> ## severity の基準（`kind: "violation"` のとき）
>
> - **5**: 確実に壊れる。存在しない API・prop・値（型定義で確かめたもの）、eslint-plugin-smarthr のルールへの違反（ガイドにルール名があるもの）。a11y に関わる指摘でも、これら以外はガイドの印で 4 以下を付けてください
> - **4**: ガイドが `[must]` とする決まりへのはっきりした違反（例: 1 つの画面に Primary のボタンが複数、別のページへの移動に Button を使う）
> - **3**: ガイドが `[should]` とする推奨に反する。より良い選び方がある
> - **2**: ガイドが `[avoid]` とする軽いアンチパターン
> - **1**: 好みの範囲の提案
>
> 迷ったら低い方を付けてください。同じルールの指摘には同じ severity を付けてください。
